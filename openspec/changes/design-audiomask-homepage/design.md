# Design

## Context

См. мотивацию и границы в [proposal.md](proposal.md). Это первый frontend-change: существующих capability-спецификаций нет. Изучены AGENTS.md, конфигурация `spec-driven` и документация Harness; рабочая интеграция с backend не предоставлена. Документ проектирует будущее поведение, не утверждает наличие готового приложения.

Сейчас создаются только документы. Основные правила поведения определены в трёх delta specs. Неизвестные форматы, лимиты и параметры не становятся значениями по умолчанию. Контракт демаскирования не требуется этому change.

Первый этап этого change — реализация и самостоятельная приёмка React/TypeScript-интерфейса с явно обозначенными тестовыми адаптерами, без обязательного backend. Второй этап — подключение реальных API, алгоритма, PESQ/ViSQOL и LLM — оформляется отдельной будущей спецификацией. Здесь задаются только граница адаптеров и поведение интерфейса.

## Goals / Non-Goals

**Goals:** отделить компоненты от API и состояния операций; сделать основной процесс однозначным; сохранить доступность результата при сбоях дополнительных функций; определить визуальное направление и проверяемые сценарии.

**Non-Goals:** выбор библиотек компонентов, нового стека, модели LLM, реальных endpoints и протокола задач; создание кода, логотипов-файлов, заглушек и зависимостей в текущем поручении. Остальные исключения перечислены в proposal.

## Decisions

### 1. Структура страницы и компонентов

Предлагаемая декомпозиция для будущего React/TypeScript frontend:

| Компонент | Ответственность |
|---|---|
| PageShell | Общая ширина страницы, тема, семантические landmarks. |
| Header / ThemeToggle | Текстовый знак AudioMask с простым геометрическим логотипом, якорная навигация, переключатель темы. |
| ProcessingWorkspace | Единственная область основного процесса; выбирает форму либо результат по состоянию. |
| UploadForm / FileDropzone | Выбор одного файла, сообщения выбора; кнопка доступна независимо от drag-and-drop. |
| AudioFileSummary | Имя, размер, длительность, стандартный плеер предпрослушивания. |
| MaskingParameters | Раскрываемый блок; при неизвестном контракте только пояснение о недоступности настроек. |
| OperationStatus | Безопасные сообщения реального состояния и ошибок маскирования. |
| ResultView / AudioComparison | Два отдельно подписанных стандартных плеера, скачивание и действия возврата. |
| QualityPanel | Явный запрос PESQ/ViSQOL, отдельные состояния каждой метрики. |
| TranscriptionPanel | Выбор источников, явный запуск, тексты и копирование отдельно для каждого источника. |
| HowItWorks / About / Footer | Три шага, краткое описание исследования и компактная подпись AudioMask. |

Рабочая область начинается сразу после компактной шапки и короткого заголовка «Маскирование аудиозаписи». Большого рекламного hero нет. Anchor «Обработка» ведёт к одной области и после перехода к результату.

```text
Шапка: AudioMask | Обработка · Как это работает · О проекте | Тема
Главный заголовок + короткое пояснение
┌ Основной рабочий блок ───────────────────────────────────┐
│ ФОРМА                              ИЛИ РЕЗУЛЬТАТ        │
│ Выбор / сведения / предпрослушивание    Оригинал         │
│ Параметры                              После маскирования│
│ Начать маскирование / статус            Действия         │
│                                        Качество         │
│                                        Транскрибация    │
└─────────────────────────────────────────────────────────┘
Как это работает: 1. Выберите  2. Маскируйте  3. Прослушайте и скачайте
О проекте
Компактный footer
```

Постоянное отображение формы рядом с готовым результатом отклонено: оно создаёт неоднозначность активного файла. Многостраничный wizard отклонён: согласована одна страница.

### 2. Визуальный язык Audio Studio

Панели напоминают аккуратные модули студийной аппаратуры: тонкие границы, компактные статусные подписи, умеренное скругление около 12 px и ясная иерархия. Без аудиоволн, декоративных спектрограмм, вымышленных индикаторов сигнала и процентов. Логотип не должен изображать результат анализа записи.

Предлагаемые стартовые токены для дальнейшей проверки контраста:

| Роль | Светлая тема | Тёмная тема |
|---|---|---|
| Фон страницы | `#F3F6F8` | `#0D1625` |
| Поверхность панели | `#FFFFFF` | `#182432` |
| Основной текст | `#172B3A` | `#EAF2F7` |
| Вторичный текст | `#526575` | `#B4C3CE` |
| Основное действие | `#075E78`, белый текст | `#45D3C2`, тёмный текст |
| Бирюзовый акцент | `#087F80` | `#45D3C2` |

Цвета — проектное направление, соответствие контрасту ещё не проверено. Состояния ошибок передаются текстом и значком, а не одним цветом. Типографика — локальный системный sans-serif с кириллицей без загрузки внешних шрифтов; заголовки 28–36 px на ПК, 24–28 px на мобильном, основной текст 16 px. Интервалы кратны 4/8 px. Максимальная ширина контента ориентировочно 1120 px.

Утверждены две темы и переключение без сброса рабочего состояния. При каждой загрузке страницы тема определяется через `prefers-color-scheme`: системная тёмная открывает тёмную Audio Studio, системная светлая — светлую. До ручного выбора интерфейс учитывает изменения системной темы в обе стороны. После первого ручного переключения актуальная вручную выбранная тема имеет приоритет до перезагрузки, последующие системные изменения её не переопределяют. Переключатель остаётся доступен, включая время обработки.

Выбор хранится только в состоянии открытой страницы. Для настройки темы запрещены чтение/запись `localStorage`, `sessionStorage`, cookies и серверное хранение. После перезагрузки ручной приоритет сбрасывается, заново применяется текущая системная тема и возобновляется следование её изменениям до нового ручного выбора. Это окончательно утверждённое поведение, не открытое решение.

### 3. Состояния и переходы рабочего блока

| Состояние | Что отображается | Переход |
|---|---|---|
| empty | Форма выбора | Выбор → readingMetadata. |
| readingMetadata | Форма, имя/размер, загрузка реальных метаданных | Успех → ready; ошибка → сообщение с доступными данными. |
| ready | Форма с исходником и предпрослушиванием | Явный запуск при доступном контракте → processing. |
| processing | Та же форма и статус; выбор, удаление, замена файла, drop и повторный запуск недоступны | Успех → result; ошибка → formError; в обоих случаях блокировка снимается. |
| formError | Форма с сохранённым исходником и ошибкой | Исправление/повтор → ready/processing; другой файл → readingMetadata. |
| result | Только результат с плеерами и дополнительными панелями | Возврат/повтор → ready; другой файл → empty. |

Состояние загрузки файла на сервер и преобразования показывается отдельно только если backend действительно различает эти стадии. Браузерное чтение метаданных не означает подтверждённую поддержку backend. Неопределённая длительность обозначается текстом, а не «0:00» как вычисленным значением. Поведение запуска при браузерной несовместимости окончательно определяется поддержкой backend: сама ошибка локального плеера не доказывает невозможность обработки.

«Вернуться к форме» и «Обработать ещё раз» сохраняют исходник и не запускают задачу автоматически; второе действие переводит фокус к параметрам/кнопке запуска. В форме появляется действие «Открыть текущий результат»: оно скрывает форму, возвращает прежние плееры и скачивание без новых запросов. Результат текущей обработки остаётся в состоянии открытой страницы до замены новым успешным результатом; ошибка повторной попытки его не удаляет. «Загрузить другой файл» начинает новое рабочее состояние без доступа к прежнему результату и без команды серверного удаления. История, личный кабинет, серверное сохранение и восстановление после перезагрузки страницы не добавляются.

Пока маскирование выполняется, выбор, удаление и замена исходника блокируются: недоступны кнопки и файловый input, drag-and-drop не принимает новый файл и не меняет исходник. Блокировка действует для мыши и клавиатуры, а защита обработчиков исключает обход через события drop и повторный запуск. Показывается понятное пояснение временной недоступности. После успеха или ошибки блокировка снимается: на результате работа с файлом доступна через возврат к форме и выбор другого файла, при ошибке — в сохранённой форме. Отмена обработки не добавляется без отдельного согласования. Возврат к форме и смена темы не означают запрос удаления данных.

Метрики и транскрибация имеют отдельные состояния `idle`, `loading`, `success`, `error`, `unavailable`, а транскрипция также `empty`. Для каждой метрики и каждого источника транскрибации результат хранится отдельно. Ошибка одной панели не изменяет состояние скачивания или другой панели. Поздние ответы связываются с идентификаторами записи, результата и запроса, не применяются к новой версии.

Альтернатива одного общего флага loading отклонена: ошибка транскрибации тогда могла бы блокировать доступное аудио.

### 4. Абстрактные интерфейсы будущего backend

Контракты ниже концептуальные: это не утверждённые HTTP endpoints или сигнатуры алгоритма. В текущем change их роль выполняют тестовые адаптеры; таблица не требует реальных интеграций для приёмки frontend.

| Возможность адаптера | Вход | Ожидаемые данные/состояния |
|---|---|---|
| Доступность сервиса | Контекст текущей сессии | Доступность маскирования, метрик, локальной транскрибации; согласованные ограничения и описания параметров при наличии. |
| Подготовка исходника | Выбранный File | Непрозрачный идентификатор записи, реальные метаданные, доступность воспроизведения; валидационная ошибка. Конвертация — ответственность backend. |
| Маскирование | Идентификатор исходника и только согласованные параметры | Подтверждённые состояния операции, ошибка/недоступность либо идентификатор результата и ссылки для плеера/скачивания. |
| Оценка качества | Идентификаторы согласованной пары и версия результата | PESQ/ViSQOL отдельно: реальное значение с условиями расчёта либо ошибка/недоступность. |
| Транскрибация | Идентификаторы выбранных записей | Локально полученные тексты по источникам либо отдельные состояния ошибки/недоступности. |
| Доступ к аудио | Непрозрачный идентификатор | Ресурс для воспроизведения/скачивания или безопасная ошибка доступности. |

Способ получения статуса (ответ, polling, события) согласуется позже; frontend не генерирует искусственные стадии таймером. Точные DTO, transport, коды ошибок, MIME, поддерживаемые форматы и лимиты определяются отдельным контрактом с backend. Произвольные внутренние пути и секреты в UI не передаются. Клиентские object URL предпрослушивания освобождаются после прекращения использования, без удаления исходных и серверных файлов.

Без реального backend и с выключенным тестовым режимом UI явно показывает недоступность. Первый этап проверяет весь интерфейс через изолированные тестовые адаптеры: успех, ошибку, недоступность, частичные и поздние ответы. В тестовом режиме постоянно видна маркировка «Тестовые данные — обработка не выполнялась», также у результата, метрик и транскрипций; при скачивании разрешённой фикстуры явно указано, что файл тестовый. Примеры не являются настоящим маскированием, оценкой качества или распознаванием. Тестовые адаптеры не обращаются к сети, алгоритму, метрикам или LLM. В будущей спецификации реальный алгоритм подключается только через внешний адаптер по предоставленному контракту, без внешних fallback-сервисов.

### 5. Адаптивность и доступность

На широком экране плееры результата располагаются рядом, дополнительные панели — ниже. Ниже ориентировочно 768 px всё становится одной колонкой, кнопки занимают доступную ширину, навигация переносится без скрытия разделов. Проверяемые размеры: 360×800 и 1440×900 CSS px, дополнительно увеличение текста/масштаба до 200%. Плееры ограничены шириной контейнера, длинные имена файлов переносятся. Нет фиксированной высоты рабочего блока и горизонтального скролла.

Семантические header/nav/main/section/footer, один h1; skip-link к рабочей области. Drag-and-drop дополняется подписанным input; параметры используют доступное раскрытие. Все кнопки имеют понятные русские подписи, переключатель темы — доступное имя и состояние. Radio group источников транскрибации имеет legend. Цели касания ориентировочно от 44×44 px.

Требуется WCAG 2.2 AA по применимым критериям: контраст текста минимум 4.5:1 (крупного 3:1), значимых границ/фокуса 3:1; управление клавиатурой, видимый фокус. Статусы объявляются через доступную live-область, ошибки связываются с соответствующим действием, фокус при успехе переводится на заголовок результата, при возврате — к форме. Учитывается reduced-motion; звук сам не запускается. Стандартные браузерные controls используются во всех плеерах. Оценка соответствия требует будущих проверок, сейчас она не заявляется.

### 6. Критерии приёмки

Сценарии всех трёх specs являются критериями интерфейса. В этом change они проверяются через явно обозначенные тестовые адаптеры; упоминания сервисов описывают входные ответы интерфейса, а не требование подключить backend. Будущая приёмка frontend дополнительно проверяет:

1. На ПК и смартфоне рабочий блок находится в начале страницы: при первом открытии показана форма, после успеха — результат. Навигация ведёт к тем же разделам в обоих состояниях.
2. В DOM и доступном представлении рабочего блока нет одновременно активных формы и результата.
3. Нет автоматических запросов метрик/LLM, вымышленных процентов и параметров. Значения и тексты тестовых адаптеров имеют явную маркировку и не выдаются за вычисленные результаты.
4. Успех, ошибка, недоступность, частичные и запоздалые ответы проверены изолированными тестовыми адаптерами; ошибочные ответы не заменяют другие успешные данные.
5. Тексты копируются по источникам; ошибка буфера обмена оставляет возможность выделить текст.
6. Обе темы, клавиатура, фокус, доступные статусы, длинные имена и узкий экран проверены без обязательного наличия backend.
7. В UI нет незаявленных функций, внешней отправки аудио, внутренних путей или секретов. Серверное хранение не реализовано, произвольный срок хранения не заявлен.
8. Возврат к форме и «Открыть текущий результат» проверены: каждый переход заменяет содержимое рабочего блока без повторной обработки и истории.
9. При свежей загрузке проверены светлое и тёмное системные предпочтения; до ручного выбора смена `prefers-color-scheme` в обе стороны меняет тему без сброса процесса. После ручного выбора системные изменения не переопределяют тему, ручной переключатель продолжает работать.
10. После перезагрузки применяется текущая системная тема, ручной выбор сбрасывается и следование системе возобновляется. Настройка темы не читается и не записывается в localStorage, sessionStorage, cookies или сервер; достаточно состояния открытой страницы.
11. На тестовом адаптере с удерживаемым состоянием обработки проверены блокировка выбора, удаления, замены исходника, файлового input, drag-and-drop и повторного запуска. Исходник не меняется, дополнительный запрос не создаётся; обход мышью, клавиатурой и drop невозможен, отмены нет.
12. Отдельно проверены успех и ошибка: оба снимают блокировку. После успеха доступна работа с файлом через действия результата, после ошибки — в форме; повторный запуск требует явного действия и доступного адаптера.

## Risks / Trade-offs

- [Неизвестные backend-контракты] → изолированные интерфейсы; явная недоступность; согласование до интеграции.
- [Внешний вид стандартных controls зависит от браузера] → сохранять нативную семантику и тестировать целевые браузеры вместо аудиоволн и собственного сложного плеера.
- [Ошибка или истечение доступности ресурса] → безопасная ошибка без удаления прочих результатов; срок хранения не назначается frontend.
- [Преобразования WAV меняют исследуемые данные] → не выполнять их в браузере, условия метрик и преобразования согласовывать отдельно.
- [Непроверенные Hooks в VS Code] → защищённые операции будущей разработки выполнять через `codex-local`, не полагаться только на сообщения Hooks.

## Migration Plan

Миграция текущего приложения не требуется: change задаёт первую страницу. После отдельного разрешения реализовывать по tasks только frontend с тестовыми адаптерами и принимать его независимо от backend. Реальные интеграции планируются и принимаются во втором этапе по отдельной будущей спецификации. Публикацию выполняет пользователь. Тестовый режим не является способом скрыть недоступность реального сервиса.

## Open Questions

Следующие вопросы относятся ко второму этапу и отдельной будущей спецификации; они не блокируют самостоятельную приёмку frontend с тестовыми адаптерами:

- Допустимые форматы, предел размера, поведение конвертации и требования WAV.
- Контракт маскирования: вызов, параметры, результат, ошибки и реальная доступность; без доступа к исходникам.
- Срок доступности файлов, условия удаления и сообщение пользователю; без произвольного срока хранения.
- Сравниваемая пара PESQ/ViSQOL, режимы и преобразования. Оригинал и маскированный результат не назначаются парой автоматически.
- Локальная мультимодальная LLM, требования её подключения и ограничения распознавания.
- Контракты API/DTO, статусы задач и выдача ресурсов.

Целевые браузеры для проверки нативного воспроизведения уточняются перед реализацией интерфейса.

До реализации соответствующих частей эти решения согласовываются; отсутствие ответа не считается согласием. Новые решения, меняющие поведение, требуют обновления planning-артефактов до кода.
