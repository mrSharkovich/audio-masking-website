# Инструкции для coding agent

## Проект и область действия

Название курсового проекта: «Сайт маскирования аудиозаписей».

Назначение: веб-платформа для исследования эффективности алгоритма маскирования аудиозаписей.

Этот файл задаёт правила работы coding agent во всём репозитории. Следуй текущей задаче пользователя и не расширяй её самостоятельно. Общий перечень функций ниже определяет границы проекта, но не является поручением реализовать всё сразу.

Общайся с пользователем на русском языке. Пиши понятный, поддерживаемый код; используй последовательные и осмысленные имена модулей, функций и переменных.

## Доступы и ограничения Codex

1. Codex может самостоятельно создавать и редактировать файлы проекта, писать код и запускать локальные тесты в пределах текущей порученной задачи. Это разрешение не расширяет согласованный объём работы и не отменяет раздел «Границы текущего этапа».
2. Codex запрещено получать доступ к исходникам закрытого алгоритма маскирования, в том числе запрашивать или читать их. Для подключения используй только предоставленный пользователем контракт вызова и отдельный адаптер согласно разделу «Закрытый алгоритм маскирования».
3. Codex запрещено взаимодействовать с GitHub любым способом, в том числе выполнять `git push`, `git pull`, `git fetch`, использовать GitHub API, GitHub MCP и GitHub CLI. Локальные `git status` и `git diff` разрешены. Все публикации пользователь выполняет самостоятельно.
4. Codex запрещено удалять важные файлы и каталоги без явного разрешения пользователя. Правила очистки промежуточных аудиофайлов и согласования удаления сохраняемых записей определены в разделе «Работа с аудио, метриками и LLM»; они не разрешают удаление важных файлов проекта.
5. Codex запрещено использовать платные API и совершать любые платные операции без предварительного согласования с пользователем.
6. Запрещено отправлять пользовательские аудиозаписи внешним сервисам. Для LLM-распознавания речи пока предусматривай только локальную обработку. Любое изменение этой политики требует предварительного согласования с пользователем.
7. После завершения значимой задачи напоминай пользователю самостоятельно опубликовать изменения на GitHub. Не выполняй публикацию.

## Согласованная функциональность

1. Загрузка аудиофайлов с автоматической конвертацией поддерживаемых форматов в WAV.
2. Прослушивание аудиозаписей.
3. Маскирование и демаскирование с помощью существующего Python-алгоритма.
4. Расчёт метрик PESQ и ViSQOL.
5. Распознавание речи с помощью мультимодальной LLM.
6. Прослушивание и скачивание результатов обработки.
7. Адаптивный интерфейс для ПК и смартфонов.

Не добавляй несогласованные функции, в том числе WER, CER и дополнительные AI-функции. Распознавание речи — единственная согласованная функция на основе LLM. Не добавляй автоматически авторизацию, платёжные функции, административные панели или другие самостоятельные подсистемы.

Если требование неоднозначно и выбор влияет на поведение продукта, уточни его до реализации соответствующей части. Не считай отсутствие ответа согласованием. Обычные технические решения в пределах поставленной задачи принимай самостоятельно.

## Предварительный технологический стек

- Frontend: React + TypeScript.
- Backend: Python + FastAPI.
- Обработка форматов аудио: FFmpeg.

Считай стек предварительным ориентиром. Изменение стека или добавление существенных инфраструктурных компонентов сначала обсуждай с пользователем. Подключай зависимости только по необходимости для текущей задачи; не создавай каркас всего приложения без отдельного поручения.

## Закрытый алгоритм маскирования

- Алгоритм существует отдельно от репозитория. Его исходный код закрыт; известно, что он принимает WAV-файл.
- Не публикуй, не копируй в репозиторий и не изменяй исходный код алгоритма. Не включай его в коммиты, документацию, тестовые данные или сообщения пользователю.
- Предусмотри отдельный интерфейс и адаптер для подключения алгоритма к backend. Остальные модули должны работать через этот интерфейс, без зависимости от внутренней реализации алгоритма.
- Перед реальным подключением выясни способ вызова, требования к WAV, параметры, формат результата и поведение при ошибках. Отдельно уточни контракт демаскирования. Не выдумывай эти сведения.
- Пути к внешнему алгоритму и необходимые параметры подключения задавай через конфигурацию окружения. Не фиксируй локальные пути и секреты в коде.
- Пока алгоритм недоступен, используй тестовые заглушки для проверки интерфейса. Не выдавай заглушку за настоящее маскирование или демаскирование; в рабочем приложении явно сообщай о недоступности подключения.

## Модульная архитектура

Разделяй интерфейс пользователя, HTTP API, прикладную логику и подключения внешних инструментов. На backend выделяй независимые модули по мере реализации:

- загрузка, проверка и конвертация аудио;
- адаптер маскирования и демаскирования;
- расчёт PESQ и ViSQOL;
- адаптер распознавания речи через мультимодальную LLM;
- выдача аудио для прослушивания и скачивания.

На frontend отделяй компоненты интерфейса от работы с API и состояния обработки. Не помещай всю логику в один компонент или обработчик запроса. Создавай только те модули и абстракции, которые нужны реализуемой задаче.

Используй явные контракты и типы данных на границах модулей. Проверяй входные данные на backend и возвращай понятные ошибки. Не передавай в пользовательский интерфейс секреты, внутренние пути или подробности внутренних исключений.

## Работа с аудио, метриками и LLM

- Список поддерживаемых форматов и ограничения загрузки должны быть явно определены при реализации. Не заявляй поддержку формата без проверки конвертации.
- Проверяй содержимое загружаемого файла, а не только расширение. Запускай FFmpeg с отдельными аргументами без подстановки пользовательских данных в shell-команду.
- Разделяй промежуточные рабочие файлы и аудиофайлы, доступные пользователю. Удаляй промежуточные файлы после обработки или при ошибках, только когда они больше не нужны последующим операциям.
- Сохраняй исходные записи и результаты, необходимые для прослушивания, скачивания и дальнейшей обработки, в течение согласованного срока доступности. Не удаляй их сразу после завершения обработки или HTTP-запроса. Очистка не должна прерывать активное прослушивание, скачивание или обработку. Ошибка отдельной операции не должна удалять ранее доступные результаты.
- До реализации хранения согласуй с пользователем срок доступности аудиофайлов и условия их удаления; явно сообщай эти условия в интерфейсе. Не вводи произвольный срок хранения или бессрочное хранение без согласования.
- Не добавляй пользовательские аудиозаписи и результаты обработки в систему контроля версий.
- Требования к частоте дискретизации, числу каналов и представлению WAV определяй по контрактам алгоритма и метрик. Не выбирай преобразования, влияющие на результаты исследования, без обоснования и согласования существенных решений.
- Реализуй PESQ и ViSQOL через отдельные адаптеры. Явно определяй сравниваемые записи и условия расчёта; не подменяй метрики приближёнными или вымышленными значениями. Отсутствие зависимости или невозможность расчёта показывай как явную ошибку или недоступность результата.
- Не выбирай самостоятельно поставщика и модель LLM или платный сервис. До реального подключения согласуй эти решения с пользователем. Соблюдай политику локальной обработки аудио и согласования платных операций из раздела «Доступы и ограничения Codex». Тесты должны использовать заглушки и не выполнять платные или внешние вызовы по умолчанию.
- Храни ключи доступа вне репозитория. Не записывай аудио, распознанный текст и секреты в логи без необходимости для согласованной задачи.

## Процесс разработки

1. Перед работой изучи текущее состояние репозитория и относящиеся к задаче инструкции. Сохраняй изменения пользователя; не перезаписывай и не откатывай их без указания.
2. Перед существенными изменениями предложи краткий план: какие части будут изменены, какие зависимости нужны и как будет проверен результат. К существенным относятся создание каркаса приложения, изменение архитектуры или API, интеграция внешних систем и добавление крупных функций.
3. Если план требует расширения согласованной функциональности или решения, которое должен принять пользователь, сначала получи согласование. Само требование предложить план не означает, что для каждой технической правки нужно отдельное разрешение.
4. Реализуй только текущую задачу небольшими, связанными изменениями. Не выполняй попутный рефакторинг без необходимости.
5. Добавляй тесты для реализуемой функциональности и исправляемых ошибок. Обновляй документацию при изменении поведения, настроек или способа запуска.
6. После реализации выполни подходящие проверки и изучи их результат. Исправь обнаруженные проблемы в пределах задачи.
7. Сообщи пользователю, что изменено, какие проверки выполнены и каков их результат. Если проверку выполнить невозможно, укажи причину и оставшиеся ограничения. Не утверждай, что проверка пройдена, если она не запускалась.

## Тестирование и проверка результата

- Проверяй наблюдаемое поведение и контракты, а не внутреннее устройство реализации.
- Для backend проверяй успешные сценарии, некорректные файлы, ошибки обработки и недоступность внешних компонентов по мере реализации соответствующей функциональности.
- Для frontend проверяй основные действия пользователя, состояния загрузки, обработки, результата и ошибки. При изменении интерфейса проверяй его на размерах экрана ПК и смартфона.
- Проверяй интеграцию с FFmpeg, метриками и закрытым алгоритмом отдельно от тестов с заглушками. Явно сообщай, какие реальные интеграции проверены, а какие недоступны.
- Используй небольшие синтетические или разрешённые тестовые аудиофайлы. Не используй закрытый алгоритм как тестовую фикстуру и не включай приватные записи в репозиторий.
- Запускай применимые тесты, проверку типов, линтер и сборку, если они настроены и относятся к изменённой части проекта. Для правок только документации достаточно проверки содержания и diff; не добавляй ради них код или тестовую инфраструктуру.
